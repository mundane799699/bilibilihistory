# 历史记录关键词搜索、日期筛选与分页设计方案

> 文档状态：已实现并完成生产索引迁移，待应用部署与生产验收
> 编写日期：2026-08-22
> 适用页面：`/dashboard`

## 1. 结论

在历史记录卡片列表上方增加一条筛选工具栏，提供：

- 一个关键词输入框，同时匹配视频标题、UP 主名称和分区标签。
- 一个日期范围选择器，支持选择单日或起止日期。
- 一个仅在存在筛选条件时出现的“清除筛选”操作。
- 当前筛选结果总数，用于说明筛选是否生效。
- 一组显式分页控件，支持上一页、下一页、页码选择和指定页跳转。
- 每页条数选择器，提供 20、50、100 三档，默认每页 20 条。

筛选必须由服务端完成，并同时作用于列表查询与总数统计。现有无限滚动改为服务端分页，切换页码后用该页数据替换卡片列表，不再通过滚动自动追加。

推荐先实现下述最小完整版本，不在本次加入高级语法、搜索历史、排序切换或按视频类型筛选。

## 2. 现状与问题

当前实现涉及以下文件：

- `app/dashboard/page.tsx`：维护列表、分页状态和基于 `IntersectionObserver` 的无限滚动。
- `app/api/history/route.ts`：处理 `GET /api/history`，只接收 `page`、`pageSize`。
- `lib/db/queries.ts`：分页数据查询和总数查询目前都只按 `user_id` 过滤。
- `lib/db/schema.ts`：`view_at` 是 Unix 秒时间戳，类型为 `bigint`。

页面已经声明 `keyword`、`authorKeyword`、`date` 及防抖状态，但没有渲染筛选控件，也没有把条件发送给 API。因此状态变化只会重复请求同一批无筛选数据。现有 `searchHistory` 函数虽然可以匹配标题、作者和标签，但没有分页、日期条件及同条件计数，不能直接满足本功能。

另有三个与本功能相关的问题应在实现时一并处理：

1. 快速改变筛选条件时，旧请求可能晚于新请求返回并覆盖最新结果。
2. 当前仅按 `view_at DESC` 排序；时间相同的记录顺序不稳定，分页边界可能重复或遗漏。
3. 当前虽有服务端 `page`、`pageSize` 参数，但前端固定每页 100 条，只能自动加载下一页，用户不能查看当前页、选择每页条数或直接跳页。

## 3. 目标与非目标

### 3.1 目标

- 用户可以用一个关键词查找自己的全部历史记录，而不是只查已加载页面。
- 用户可以筛选某一天或一个连续日期范围内的观看记录。
- 关键词与日期条件可组合，组合关系为 AND。
- 用显式翻页替换无限滚动，并支持设置每页条数和跳转到指定页。
- 筛选、页码、每页条数和结果总数保持一致，删除记录后页码能自动纠正。
- 桌面与移动端都能清晰使用，键盘操作和读屏标签完整。
- API 参数可验证，查询始终限定为当前登录用户。

### 3.2 非目标

- 不做全文分词、拼音、同义词、模糊纠错或搜索结果高亮。
- 不增加作者独立筛选框；作者已纳入统一关键词搜索。
- 不增加视频类型、分区多选或排序方式切换。
- 不改变历史记录上传、删除或会员限制逻辑。
- 不在本次把 offset 分页整体迁移为游标分页。

## 4. 交互设计

### 4.1 页面布局

工具栏放在卡片网格上方，与当前内容区同宽，并在滚动列表时保持普通文档流，不做吸顶，避免和现有顶部导航争夺纵向空间。

桌面端示意：

```text
┌─────────────────────────────────────────────────────────────────┐
│ 🔍 搜索标题、UP 主或分区… │ 搜索 │ 📅 2026-08-01 至 2026-08-22 │ 清除 │
└─────────────────────────────────────────────────────────────────┘
  找到 128 条记录

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ...
│ 历史记录卡片 │ │ 历史记录卡片 │ │ 历史记录卡片 │
└──────────────┘ └──────────────┘ └──────────────┘

  共 128 条  每页 [20⌄] 条     [‹] [1] [2] [3] … [7] [›]  前往 [  ] 页
```

移动端将关键词框占满一行，日期按钮和清除按钮放在下一行；结果数独占一行。分页区分两行展示：第一行是上一页、`当前页/总页数`、下一页，第二行是每页条数和跳页输入。移动端省略完整数字页码列表，但保留指定页跳转。控件不应缩窄到难以点击。

### 4.2 关键词搜索

- 占位文案：`搜索标题、UP 主或分区`。
- 匹配字段：`title`、`author_name`、`tag_name`。
- 匹配方式：忽略英文大小写的连续子串匹配；中文直接按原文匹配。
- 输入首尾空白在请求前移除，内部空白保留。
- 空字符串等同于无关键词条件。
- 最长 100 个字符；超过长度时前端阻止继续输入，API 仍独立校验。
- 输入只更新草稿值；点击“搜索”按钮或按 Enter 后才提交并请求，提交后回到第 1 页。
- 输入框右侧在有内容时显示清空按钮；按 `Escape` 也可清空草稿。清空后仍需显式提交才会改变搜索结果。

首版将完整关键词作为一个连续子串处理，不拆分多个词，也不赋予标题、作者、标签不同权重。这样行为更可预测，且列表仍按观看时间排序，而不是按相关度排序。

### 4.3 日期范围

- 默认未选择，不限制日期。
- 点击日期按钮打开区间日历，可选择单日或起止日期。
- 只选择一天时，筛选该日 00:00:00（含）至次日 00:00:00（不含）。
- 选择范围时，包含开始日和结束日的完整自然日。
- 不允许结束日期早于开始日期。
- 可选未来日期，但通常得到空结果；首版无需专门禁用。
- 日期按钮文案：未选择时为 `筛选日期`；单日显示 `YYYY-MM-DD`；范围显示 `YYYY-MM-DD 至 YYYY-MM-DD`。
- 日历内提供“清除日期”，工具栏的“清除筛选”则同时清除关键词和日期。

“自然日”以用户浏览器当前时区为准，与卡片中 `toLocaleString()` 展示出的观看日期保持一致。前端不要使用 `new Date("YYYY-MM-DD")` 解析日期，因为该形式按 UTC 解释，可能产生跨日；应使用年、月、日构造本地午夜。

前端把日期转换为 Unix 秒后发送：开始时刻为 `startAt`（含），结束日期的次日本地午夜为 `endAt`（不含）。使用半开区间可以避免 `23:59:59.999` 精度和边界问题。

### 4.4 分页

卡片网格下方增加分页区，桌面端从左到右包括：

- 总数：`共 N 条`。
- 每页条数选择器：`20`、`50`、`100`，默认 `20`。
- 上一页和下一页按钮。
- 数字页码：始终展示第 1 页、最后一页、当前页及当前页前后各 2 页，中间断档用省略号表示。
- 指定页跳转：数字输入框和“跳转”按钮。

交互规则：

- 当前页按钮使用选中样式，并设置 `aria-current="page"`。
- 第 1 页禁用“上一页”，最后一页禁用“下一页”；无结果时整组翻页操作禁用。
- 点击页码、上一页或下一页立即发起请求，并把页面滚动到卡片列表顶部。
- 跳页输入只接受正整数；按 Enter 或点击“跳转”提交。
- 跳页为空、非整数、小于 1 或大于总页数时不发送请求，在输入框附近显示 `请输入 1–N 之间的页码`。
- 当总页数只有 1 页时，保留总数和每页条数选择器，隐藏页码、上一页、下一页和跳页区域。
- 修改每页条数后回到第 1 页并重新请求，不尝试维持原卡片在新页中的位置。
- 修改关键词或日期后回到第 1 页；当前每页条数保持不变。
- 页码切换期间禁止再次提交同一个页码，但允许用户选择其他页；新请求会取消旧请求。
- 分页使用现有 offset 方案，计算方式为 `(page - 1) * pageSize`。显式翻页每次替换整页数据，不再追加列表。

桌面端数字页码示例：

```text
当前第 1 页，共 12 页：  [1] [2] [3] … [12]
当前第 6 页，共 12 页：  [1] … [4] [5] [6] [7] [8] … [12]
当前第 12 页，共 12 页： [1] … [10] [11] [12]
```

### 4.5 状态反馈

- 初次进入页面：显示现有加载态，加载完成后展示全部记录总数。
- 改变筛选条件：保留工具栏和分页区，列表区域展示加载状态；请求成功后滚动到内容区顶部。
- 切换页码或每页条数：列表区域展示加载状态，旧页面内容不得与新页码同时显示。
- 有结果：筛选工具栏下显示 `找到 N 条记录`，分页区显示 `共 N 条，第 X/Y 页`。
- 无筛选且无数据：`暂无历史记录`。
- 有任意筛选但无结果：`没有找到匹配的历史记录`，并提供“清除筛选”。
- 请求失败：列表区域展示 `加载失败，请重试`，保留当前筛选条件，不将错误误报为空结果。
- 删除记录成功：重新请求当前页，保证当前页被后一条记录补齐。若删除后当前页超过新的总页数，则跳到新的最后一页；删除唯一一条记录后停留第 1 页并展示空状态。

## 5. URL 与页面状态

首版建议把已提交的筛选条件同步到 URL 查询参数，以便刷新、前进后退和复制链接后保留条件：

```text
/dashboard?q=chatgpt&from=2026-08-01&to=2026-08-22&page=3&pageSize=50
```

- `q`：去除首尾空白后的关键词。
- `from`、`to`：供页面展示和恢复日历状态的本地日历日期，格式为 `YYYY-MM-DD`，`to` 对用户是包含关系。
- `page`：当前页；第 1 页时省略。
- `pageSize`：每页条数；默认值 `20` 时省略，可选值为 `20`、`50`、`100`。
- 关键词或日期改变时将 `page` 重置为 1；清除筛选也回到第 1 页，但保留用户选择的 `pageSize`。
- 修改 `pageSize` 时将 `page` 重置为 1。
- 关键词显式提交和日期变化使用 `router.replace`，避免草稿输入产生浏览器历史。
- 点击页码、上一页、下一页、提交跳页或修改每页条数使用 `router.push`，使浏览器返回按钮可以回到上一页码状态。
- 刷新、前进和后退均以 URL 为准恢复筛选、页码和每页条数，再重新请求对应页面。
- URL 中的 `page` 或 `pageSize` 格式非法时，前端改回默认值并规范化 URL；如果 `page` 合法但超过接口返回的 `totalPages`，跳到最后一页并重新请求。总数为 0 时规范为第 1 页。

URL 是页面筛选和分页状态的来源，API 请求则使用页码、每页条数以及由日期转换出的 `startAt`、`endAt`。这样 URL 对人可读，同时 API 日期边界不依赖部署服务器时区。

## 6. API 设计

扩展现有接口，不新增路由：

```http
GET /api/history?page=1&pageSize=100&keyword=chatgpt&startAt=1785513600&endAt=1787414400
```

### 6.1 查询参数

| 参数 | 必填 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `page` | 否 | 正整数 | `>= 1`，默认 `1` | 当前页 |
| `pageSize` | 否 | 正整数 | `1..100`，API 默认 `50` | 每页数量 |
| `keyword` | 否 | string | trim 后 `1..100` | 标题、UP 主或标签关键词 |
| `startAt` | 否 | Unix 秒 | 非负安全整数 | 观看时间下界，包含 |
| `endAt` | 否 | Unix 秒 | 非负安全整数 | 观看时间上界，不包含 |

规则：

- `startAt` 与 `endAt` 可以单独出现，便于 API 支持开放区间；页面正常会成对发送。
- 两者同时出现时必须满足 `startAt < endAt`。
- API 为兼容现有调用继续接受 `1..100` 的任意 `pageSize`，并保留默认值 `50`；页面只提供 `20`、`50`、`100` 三个选项，页面默认 `20` 且请求时始终显式传值。
- 请求页码超过 `totalPages` 时 API 返回空 `history` 和真实分页元数据，不静默篡改请求页码；页面根据元数据跳转到最后一页。
- 不能用宽松的 `parseInt` 接受 `1abc`；应完整校验字符串为整数。
- 非法参数返回 `400`，结构保持 `{ "error": "..." }`。
- 未登录仍返回 `401`。
- 关键词中的 `%`、`_` 和反斜杠按普通字符处理，不能意外变成 SQL LIKE 通配符。

响应结构保持兼容：

```json
{
  "history": [],
  "pagination": {
    "page": 1,
    "pageSize": 100,
    "totalCount": 0,
    "totalPages": 0,
    "hasNextPage": false,
    "hasPrevPage": false
  }
}
```

`totalCount` 必须是当前用户在相同关键词和日期条件下的记录数，而不是该用户全部历史记录数。

分页元数据计算规则：

- `totalPages = Math.ceil(totalCount / pageSize)`，无结果时为 `0`。
- `hasNextPage = page < totalPages`。
- `hasPrevPage = totalPages > 0 && page > 1`。

## 7. 数据库查询设计

### 7.1 统一筛选对象

在查询层定义一个共享筛选类型，分页查询与计数查询都接收它，避免两个查询逐渐产生条件差异：

```ts
interface HistoryFilters {
  keyword?: string;
  startAt?: number;
  endAt?: number;
}
```

由一个纯函数构造 WHERE 条件，逻辑等价于：

```sql
WHERE user_id = :userId
  AND (
    title ILIKE :pattern ESCAPE '\\'
    OR author_name ILIKE :pattern ESCAPE '\\'
    OR tag_name ILIKE :pattern ESCAPE '\\'
  )
  AND view_at >= :startAt
  AND view_at < :endAt
```

只拼接实际存在的可选条件。所有值必须通过 Drizzle 参数绑定传入，不拼接原始用户输入。关键词 pattern 为转义后的 `%keyword%`。

分页列表排序改为：

```sql
ORDER BY view_at DESC NULLS LAST, id DESC NULLS LAST
```

`id DESC` 提供确定性的第二排序键。`view_at` 当前允许为 NULL，日期筛选自然排除 NULL；无日期条件时将 NULL 记录放在末尾。

### 7.2 查询函数调整

推荐收敛为以下职责：

- `getUserHistoryWithPagination(userId, page, pageSize, filters)`：返回筛选后的当前页。
- `getUserHistoryCount(userId, filters)`：返回完全相同条件下的总数。
- `buildHistoryConditions(userId, filters)`：只负责构造共享条件。

现有无分页的 `searchHistory` 没有调用方，实施时应删除或改为复用新条件，避免保留第二套搜索语义。

### 7.3 索引与性能

当前记录约 32.8 万条，现有单列 B-tree 的 `title_idx`、`author_name_idx`、`tag_name_idx` 无法有效加速前导通配符 `%keyword%` 查询；现有主键 `(id, user_id)` 也不适合以 `user_id` 为首要条件的列表访问。

本功能至少应增加一个与常用访问路径匹配的复合索引：

```sql
CREATE INDEX ... ON bilibili_history
  (user_id, view_at DESC NULLS LAST, id DESC NULLS LAST);
```

关键词索引采用分阶段策略：

1. 先在生产数据副本上用代表性的普通用户、大历史量用户、1 字符和常见关键词执行 `EXPLAIN (ANALYZE, BUFFERS)`。
2. 如果 P95 搜索耗时无法达到 500 ms，再启用 PostgreSQL `pg_trgm`，为 `title`、`author_name`、`tag_name` 增加 GIN trigram 索引。
3. 索引上线前评估体积和写入影响；生产建索引使用低峰期及适合当前迁移体系的安全方式。

不建议未经基准测试直接创建三个大型 GIN 索引。复合列表索引是本功能实现的一部分；trigram 索引是否首发由压测结果决定。

指定页跳转要求使用 offset 或等价的随机页定位，而游标分页无法直接跳到任意页。本方案继续使用 offset，因此越靠后的页需要跳过越多索引项，理论成本会随页码增长。当前数据规模下先用复合索引控制成本，并分别测试第一页、中间页和最后一页；若大历史量用户的深分页未达到性能目标，再单独设计深分页优化，不能用取消指定页跳转来规避。

## 8. 前端数据流与并发控制

建议将页面状态区分为：

- 输入态：用户正在编辑的关键词和日期。
- 已提交筛选态：用户确认后写入 URL、用于请求的条件。
- 分页态：`currentPage`、`pageSize`、`totalPages`、`totalCount`。
- 列表态：当前页 `history`、`isLoading` 和 `error`。

流程：

```text
用户提交关键词、选日期、翻页、修改每页条数或跳页
        ↓
校验交互；筛选变化和 pageSize 变化时页码归 1
        ↓
更新 URL（筛选 replace，分页 push）并取消上一请求
        ↓
按 URL 的筛选、page、pageSize 请求 API
        ↓
用响应替换整页列表和分页元数据
```

实现要求：

- 使用 `URLSearchParams` 构造请求，避免手写字符串遗漏编码。
- 新筛选请求开始时用 `AbortController` 取消旧请求；同时用请求序号保护状态，确保旧响应不能覆盖新结果。
- `getHistory` 必须显式接收筛选和分页快照，不能从可能变化的闭包读取条件。
- 每次成功响应都用 `setHistory(items)` 替换列表，不再追加，也不再维护 `hasMore`、`loadMoreRef` 或 `IntersectionObserver`。
- 筛选或每页条数改变时先把页码归 1，再发请求；纯页码变化保持筛选和每页条数不变。
- 服务端返回的 `pagination` 是总页数和按钮禁用状态的权威来源。
- 如果 URL 页码超过响应中的总页数，规范化到最后一页后再请求一次；必须设置保护，避免重定向循环。
- 跳页输入使用独立的临时字符串状态，只有提交并通过范围校验后才更新 URL，避免每输入一个数字就请求。
- 开发环境 React Strict Mode 下即使 effect 执行两次，也不能让旧响应覆盖新页面。

## 10. 测试方案

### 10.1 查询与 API

- 无筛选：结果、总数和现有行为一致。
- 只搜标题、只搜作者、只搜标签：均能命中。
- 英文大小写不同：可以命中。
- 中文、空格、emoji：正常编码并匹配。
- `%`、`_`、反斜杠、单引号：按字面匹配且不产生 SQL 注入。
- 关键词为空白：按无关键词处理。
- 关键词超过 100 字符：返回 400。
- 只传 `startAt` 或只传 `endAt`：开放区间正确。
- 单日、跨月、跨年范围：边界正确。
- `startAt = endAt`、开始晚于结束、非整数、负数、超出安全整数：返回 400。
- API 未传分页参数时保持现有行为：返回第 1 页、每页 50 条；新页面默认显式请求每页 20 条。
- `page`、`pageSize` 的非法输入返回 400；API 的 `pageSize=1` 和 `pageSize=100` 边界可用。
- 请求超过最后一页时返回空列表、真实 `totalPages` 和一致的 `hasNextPage`、`hasPrevPage`。
- 未登录用户不能借筛选参数读取数据。
- 两个用户有相同标题时，只返回当前用户记录。
- 列表与 `totalCount` 使用同一条件，最后一页 `hasNextPage` 正确。
- 多条记录 `view_at` 相同时，跨页顺序稳定。

### 10.2 前端交互

- 只输入或清空关键词草稿不会请求；点击“搜索”或按 Enter 后才请求最新关键词。
- 快速输入并清空时，慢返回的旧请求不会覆盖清空后的结果。
- 选择单日、日期范围、清除日期和清除全部筛选均正确。
- 上一页、下一页、数字页码和指定页跳转均请求正确页面并替换列表。
- 每页 20、50、100 条均可选择；改变每页条数后回到第 1 页。
- 跳页的空值、非整数、0、负数和超过总页数都显示校验提示且不请求。
- 第 1 页、最后一页、只有 1 页和 0 条结果时，分页按钮显示与禁用状态正确。
- URL 可刷新恢复，浏览器前进/后退可恢复筛选、页码和每页条数。
- 输入筛选条件后回到第 1 页但保留每页条数；各页均保持相同筛选条件。
- URL 带有超过总页数的合法页码时自动跳到最后一页；0 条结果时回到第 1 页且不循环请求。
- 有筛选的空状态与完全无历史记录的空状态文案不同。
- 请求失败显示重试，不显示“无结果”。
- 删除记录后重新请求当前页；删除最后一页最后一条记录时退到新的最后一页。
- 桌面、窄屏和触控设备布局可用；Tab、Enter、Escape 和日历键盘操作正常。

### 10.3 性能

- 使用接近生产规模的数据测试无筛选、日期筛选和关键词组合筛选。
- 对大历史量用户分别测试第一页、中间页和最后一页，记录 offset 深度对耗时的影响。
- API 服务端 P95 目标：普通筛选小于 500 ms；无筛选分页不应比当前版本明显退化。
- 确认复合索引被日期/列表查询使用。
- 若关键词查询未达标，以实测决定是否启用 trigram 索引，并记录索引体积与写入开销。

## 11. 验收标准

满足以下条件即可认为功能完成：

1. 关键词可匹配当前用户全部历史中的标题、UP 主和分区标签。
2. 单日与日期范围筛选都与卡片展示的本地日期一致，开始日和结束日均被包含。
3. 关键词和日期组合后，列表、页码、总页数和结果总数始终使用完全相同的条件。
4. 用户可通过上一页、下一页、数字页码或跳页输入访问目标页，并可选择每页 20、50、100 条。
5. 快速切换条件或页码时不会出现旧结果覆盖新页面。
6. 刷新和浏览器前进/后退可恢复筛选条件、页码和每页条数。
7. 非法参数得到 400，未登录得到 401，任何查询都不会跨用户。
8. 空状态、加载状态、错误状态和清除筛选入口完整。
9. 生产规模数据下达到约定性能目标，新增索引已通过执行计划验证。

## 12. 实施顺序与回滚

建议实施顺序：

1. 补查询条件构造器、分页/计数一致性和 API 参数校验。
2. 添加复合索引并在生产规模副本上验证执行计划。
3. 增加筛选工具栏、显式分页、URL 同步和请求取消，删除无限滚动逻辑。
4. 完成组合条件、翻页、每页条数、跳页、删除和时区边界测试。
5. 根据关键词查询实测决定是否追加 trigram 索引。

代码回滚时可恢复前端无限滚动并移除筛选参数；扩展后的 API 参数均为可选，且保留 API 默认 `pageSize=50`，因此对旧客户端向后兼容。复合索引可以保留，不影响旧查询语义。若新增 trigram 索引，回滚功能时也无需立即删除，可在确认无其他查询依赖后另行清理。

## 13. 待审查决策

本方案给出以下推荐默认值，请在进入实现前确认：

- 统一关键词框匹配标题、UP 主和分区标签，不保留独立作者输入框。
- 日期筛选采用日期范围，而不是只能选择单日。
- 日期语义跟随浏览器本地时区，与卡片当前显示保持一致。
- 页码和每页条数同步到 URL；页码导航使用浏览器历史，关键词提交使用 replace。
- 关键词最大长度 100，必须点击“搜索”或按 Enter 才提交。
- 首版按观看时间排序，不做相关度排序和关键词高亮。
- 无限滚动改为显式分页；每页可选 20、50、100 条，页面默认 20 条。
- 改变筛选条件或每页条数时回到第 1 页；删除导致页码越界时退到新的最后一页。
- 复合索引随功能上线；三个 trigram 索引由压测结果决定。
